# PGMQ 1.12/1.13 compatibility and native upgrade ownership

## Status

Accepted for implementation, 2026-09-10. Implementation is tracked by
[MasterPlan 2](../masterplans/2-support-pgmq-1-12-0-grouped-head-reads.md).
This repository has no profiled ADR bundle; this record follows its existing plain-Markdown
decision convention and introduces no OKF metadata.

## Context

PGMQ 1.12 adds grouped-head reads. PGMQ 1.13 extends partition creation with a fourth
argument, premake, adds nullable default_partition_length to metrics_result, and converts
partitioned queue identities to GENERATED BY DEFAULT so maintenance can relocate existing IDs.
The released source belongs to mori://pgmq/pgmq, tags v1.12.0 and v1.13.0. Individual source
artifact URIs are pending; the relevant project-relative files are
pgmq-extension/sql/pgmq--1.12.0--1.13.0.sql and docs/partitioned-queues.md.

Our immutable migration 0003 already makes partition creation re-entrant by guarding both
pg_partman parent registrations. Upstream 1.13 drops that three-argument function and creates
a four-argument replacement without those guards. Applying it alone loses an adopted behavior.
The 0.5.0.0 package family has already shipped separately from grouped-head support.

## Decision

Keep all existing migration bytes, order, and the 1.11 predecessor validator unchanged.
Append the upstream 1.12 upgrade, then the byte-exact 1.13 upgrade, then a local override of
create_partitioned(text,text,text,integer) that preserves the new identity declaration and
premake forwarding while restoring both parent-registration guards and retaining the queue
advisory lock. Do not restore the three-argument overload: default arguments preserve SQL
call compatibility without a competing overload. Keep local deviations separate from vendor
bytes and test their behavior in addition to allowing their bodies to differ in convergence.

Retain CreatePartitionedQueue's three fields and createPartitionedQueue's existing behavior.
Expose an explicit createPartitionedQueueWithPremake operation accepting that record and an
Int32. Explicit premake requires PGMQ 1.13; the existing operation and grouped heads work on
both 1.12 and 1.13. Add the new nullable metric to QueueMetrics as Maybe Int64. A stable
projection of the seven existing fields plus a JSON-record lookup for the optional eighth
field avoids referring to a missing 1.12 column. Nothing must not become zero: it means the
metric is unavailable on 1.12, or not applicable to a non-partitioned queue on 1.13. Just n is
a planner estimate summed over the queue and archive default partitions, not an exact count.

Add premake :: Maybe Int32 to PartitionConfig. Nothing selects the existing creation call;
Just n selects the explicit operation. Pass it through the single ReconcileOps engine and
both adapters. Like partition and retention intervals, premake applies only when creating a
queue. Existing queues are neither reconfigured nor reported as having their premake checked.
This preserves the boundary in [design note 018](../design/018-reconciliation-contract.md).

Prepare the next lockstep release as 0.6.0.0. The exported QueueMetrics, PartitionConfig and
ReconcileOps changes require migration guidance; preserve all published 0.5.0.0 changelogs.

## Consequences and verification

Tests must compare 1.12 and 1.13 schemas separately, use the appropriate three/four-argument
function identity, and inspect the eighth composite attribute. An empty-schema comparison
does not prove existing queue conversion: populate queues before upgrading, verify IDs and
payloads survive, then exercise spill relocation and maintenance with real pg_partman.
The release requires a mode that fails when pg_partman is missing rather than passing with
partition tests skipped. Refresh statistics before checking estimates, including archive rows.

The upstream ALTER TYPE is not safe for arbitrary replay; idempotence comes from the migration
ledger. Successful historical payloads must never be rewritten to repair a deployed database.
Production recovery remains an operator action, outside migration/configuration automation.

## Alternatives

Replacing the baseline breaks legacy checksum imports. Editing vendor SQL destroys provenance.
Ignoring the overwritten function regresses multi-replica creation. Replaying 0003 introduces
the wrong signature. Omitting the metric hides 1.13's observability feature. Mapping missing
metrics to zero falsely reports health. Reconfiguring pg_partman from ensureQueues expands the
existing reconciliation contract beyond this release's scope.
