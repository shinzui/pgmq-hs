# Support pgmq 1.12 and 1.13: grouped reads, partition controls, and metrics


This MasterPlan is a living document. Keep Progress, Surprises & Discoveries, Decision Log,
and Outcomes & Retrospective current. The existing filename, slug, and intention remain stable.


## Vision & Scope


Deliver the SQL and Haskell changes from upstream PGMQ 1.12.0 and 1.13.0 together. PGMQ
stores queues in PostgreSQL tables and exposes SQL functions; this repository supplies a native
SQL migration component and direct, effectful, and declarative Haskell interfaces.

PGMQ 1.12.0 supplies `read_grouped_head` and `read_grouped_head_with_poll`. They return at most
one message from each of up to `qty` groups identified by the `x-pgmq-group` header. The head is
the lowest message ID regardless of visibility: an invisible head blocks its group, expiry
makes that same head eligible again, and deleting or archiving it permits the next message.
Missing group headers share one implicit group. Polling waits inside PostgreSQL and occupies
a connection. This is a visibility lease, not a guarantee of exactly-once processing.

PGMQ 1.13.0 adds three connected capabilities. `create_partitioned` gains `premake integer
DEFAULT 4`, controlling how many partitions pg_partman creates ahead for both the queue and
archive. `metrics_result` gains an eighth field, `default_partition_length bigint`: an
estimate of rows in the queue and archive default partitions, or SQL NULL for ordinary queues.
Finally, partitioned queue `msg_id` changes from `GENERATED ALWAYS` to `GENERATED BY DEFAULT
AS IDENTITY`, including already-existing partitioned queues, so maintenance tools can move
spilled messages while retaining their IDs. These are client features as well as a server fix.

After implementation, native installs reach 1.13.0, existing native and imported 1.11 histories
upgrade safely, both Haskell APIs expose grouped heads and explicit premake, metrics preserve
the nullable estimate, and `pgmq-config` can set premake when creating queues. All six grouped
reads become reachable from `Pgmq` and `Pgmq.Effectful`. The next coordinated package release
is **0.6.0.0**: all five libraries already have 0.5.0.0 source versions and published Hackage
releases. MasterPlans 3 and 4 completed and shipped their hardening/reconciliation changes in
that release; they are baseline contracts, not unfinished release prerequisites.

Compatibility means the new client can use grouped reads, the existing three-argument
partition-creation operation, and metrics on both 1.12.0 and 1.13.0. An explicit premake call
requires 1.13.0. On 1.12.0 the new metric is unavailable and represented by `Nothing`;
on 1.13.0 `Nothing` means no default partition and `Just n` is the estimate. The native migration
component advances to 1.13.0; stopping at 1.12 is a test checkpoint, not a new public installation
mode. Keep the 1.11 predecessor validator unchanged.

In scope are tagged vendoring, append-only upgrades, preservation of local partition
re-entry hardening, Haskell statements/decoders/types, both effect interpreters, declarative
configuration, tests with real pg_partman, operator documentation, and release preparation.
Rust Queue-trait/driver additions in the two release notes are outside the SQL client scope.
Publishing to Hackage, changing existing queue partition settings during reconciliation, and
automating production partition recovery are excluded.

The authoritative source is `mori://pgmq/pgmq`. Registry discovery locates its upstream checkout
and `mori://pgmq/pgmq/docs/upstream-docs`; release evidence is upstream tag `v1.12.0` at
`08ace4087dbf00e51704c5a3d9df2e15fd566127` (July 14, 2026) and `v1.13.0` at
`32c075bb6dbed66a303d1a792393c93e36c09a97` (September 7, 2026), verified September 10.
The tagged `pgmq-extension/sql/pgmq.sql`, upgrade scripts, `pgmq-extension/test/sql/base.sql`, and
`docs/partitioned-queues.md` define the scope. These paths are relative to
`mori://pgmq/pgmq`; artifact-level URIs for individual upstream source files are pending.

No `docs/adr` corpus or profiled ADR bundle existed at refresh time. Relevant established
decisions live in [vendoring](../design/012-vendor-upstream-pgmq-sql.md),
[NULL semantics](../design/014-null-parameter-contract.md),
[notification and partition re-entry](../design/015-notification-delivery-contract.md), and
[reconciliation](../design/018-reconciliation-contract.md). The new durable compatibility and
upgrade decisions are recorded in [the 1.12/1.13 ADR](../adr/pgmq-1.12-1.13-compatibility.md).
That ADR supplements the established design notes without introducing an OKF profile.


## Decomposition Strategy


Retain four existing child plans and their paths. EP-9 owns server upgrades and the versioned
test environment. EP-10 owns the direct Haskell interface, including the 1.13 parameter and
metrics surface. EP-11 owns effectful interpretation and declarative creation, consuming EP-10's
types without redefining them. EP-12 owns umbrella reachability, documentation integration,
0.6.0.0 release preparation, and the existing in-scope consumer rollout.

This keeps each result independently demonstrable: SQL upgrades preserve real queue data;
direct calls return group heads and expose partition controls/estimates; high-level calls
preserve those results and tracing; umbrella-only client modules compile and consumers build.
There is no additional pgmq-core work stream: `QueueMetrics` actually lives in
`pgmq-hasql/src/Pgmq/Hasql/Statements/Types.hs`. The 1.13 work expands the existing concerns
enough to justify more milestones, but does not require another coordination layer.

## Integration Points


**Migration ledger and SQL ownership — EP-9.** The current manifest is `0001-install-v1.11.0.sql`,
`0002-schema-management-comment.sql`, and `0003-notify-crash-safety-and-locking.sql`. Append
the next three available numbers, currently `0004-upgrade-v1.12.0.sql`,
`0005-upgrade-v1.13.0.sql`, and `0006-preserve-partitioned-reentry-v1.13.0.sql`. Re-read the
manifest before allocating them. The first new payload is the two upstream 1.11→1.12 scripts
joined with one newline; the second is upstream's 1.12→1.13 script byte-for-byte; the third
is a separately documented local override of the new four-argument partition function.
Never edit the three existing payloads or the legacy 1.11 validator.

Unlike the 1.12 upgrade, 1.13 explicitly drops `create_partitioned(text,text,text)` and creates
the four-argument function. This removes 0003's re-entry guards. The final local override must
retain the 1.13 identity/premake changes and restore both queue and archive `part_config`
existence guards while retaining the queue advisory lock. A three-argument overload must not
be restored: SQL calls with omitted defaults resolve to the four-argument function.

**Convergence and partition test environment — EP-9 defines; EP-10/11 consume; EP-12 gates.**
Compare the 1.12 checkpoint and full 1.13 schema separately with their corresponding tagged
fresh installs. Compare bodies except for exactly identified local overrides, and compare
signatures, return types/defaults, ordered composite attributes, tables, and constraints.
The 1.12 allowlist names `create_partitioned(text,text,text)`; 1.13 names
`create_partitioned(text,text,text,integer)`. Both include `notify_queue_listeners()` and
`enable_notify_insert(text,integer)`. Allowlisting does not prove behavior: re-entry, crash
delivery, identities, and data recovery need behavioral assertions too.

EP-9 owns a repeatable test command/environment with actual pg_partman and an opt-in
`PGMQ_REQUIRE_PARTMAN=1` gate that fails if the extension cannot be installed. It also owns
test-only schema selection `PGMQ_TEST_SCHEMA_VERSION=1.12.0|1.13.0`, defaulting to the full
1.13 native ledger. These settings affect fixtures, never the public migration component.
EP-10 and EP-11 reuse this contract in their existing `test/EphemeralDb.hs` files. The release
must record both version runs and a required-partman run; a green suite with partition tests
skipped is insufficient.

**Direct API — EP-10 defines; EP-11 interprets; EP-12 exports.**

```haskell
-- Existing parameter records and encoders are reused.
readGroupedHead :: ReadGrouped -> Session (Vector Message)
readGroupedHeadWithPoll :: ReadGroupedWithPoll -> Session (Vector Message)

-- Keep CreatePartitionedQueue's existing three fields and operation.
createPartitionedQueue :: CreatePartitionedQueue -> Session ()
createPartitionedQueueWithPremake :: CreatePartitionedQueue -> Int32 -> Session ()

-- Append this field to the existing QueueMetrics record.
defaultPartitionLength :: Maybe Int64
```

The new statement takes `(CreatePartitionedQueue, Int32)` and calls
`pgmq.create_partitioned($1,$2,$3,$4)`. Explicit counts less than one remain server errors;
no call silently substitutes another value. The original statement retains three SQL
arguments and therefore works on 1.12 as well as 1.13.

EP-10 owns a stable eight-column metrics projection for both `metrics` and `metrics_all`.
Select the existing seven fields explicitly and obtain the eighth with
`(to_jsonb(m)->>'default_partition_length')::bigint`, where `m` is the returned SQL record.
That yields NULL for the missing 1.12 field without referencing a nonexistent column, and
preserves the 1.13 value. Decode it with a nullable int8 decoder; never map unavailable to zero.

**Effect and configuration — EP-11.** Add the grouped constructors and
`CreatePartitionedQueueWithPremake :: CreatePartitionedQueue -> Int32 -> Pgmq m ()`,
with the corresponding smart constructor. Plain and traced interpreters must handle it.
Existing metrics effects pass through the expanded `QueueMetrics` unchanged. Grouped spans
use Consumer/receive and both `db.operation` and `db.operation.name`; explicit premake uses
the existing partition-creation span convention and `pgmq.create_partitioned`.

Add `premake :: Maybe Int32` to `Pgmq.Config.Types.PartitionConfig`. `Nothing` calls the
existing three-argument operation; `Just n` calls the new explicit operation. Extend
`ReconcileOps` and both adapters, not two copies of the reconciliation algorithm.
Premake applies on creation only, just like partition and retention intervals; an existing
partitioned queue is skipped without changing or claiming to reconcile those settings.
The config record and backend record changes, plus the metrics record extension, require a
breaking package release.

**Release — EP-12 only.** All five libraries move 0.5.0.0→0.6.0.0 with consistent family
bounds. `pgmq-bench` keeps its version; update its bounds if necessary. Preserve all published
0.5.0.0 changelog entries and describe the new source migrations. Discover and verify consumers
with Mori and package registries at implementation time. Existing rollout scope remains
`mori://shinzui/keiro` and `mori://shinzui/shibuya-pgmq-adapter`; other discovered consumers
are recorded, not automatically brought into scope.

## Surprises & Discoveries


EP-9 implementation: the locked Nix package set supplies PostgreSQL 17.10 and pg_partman
5.4.3 through the new `partman` shell. All 11 migration tests pass with required partition
execution; both schema comparisons need exactly the planned body exceptions. The three
client fixtures now share version-selection semantics and package the exact 1.12 snapshot.
EP-10 must resolve the expected native 1.13 seven-column metrics decoder failure; all other
native hasql cases and the full effect/config suites pass. Notification crash testing now
selects its one observation column explicitly so it can validate the server upgrade independently.

The original July plan correctly found the two grouped functions, but its no-tag claim is now
historical: 1.12.0 tags the exact old SHA. The 1.13 release notes put the partition changes under
one bug-fix entry; its SQL and tests expose the new premake argument and metrics field too.
The full 1.12→1.13 fresh SQL diff changes precisely metrics_result, metrics, and
create_partitioned; the migration additionally converts existing partitioned queue identities.

The local corpus can contain newer files without corresponding local tags. Mori is used for
source discovery, while upstream remote tags determine released versions. Likewise, all five
Hackage packages now serve 0.5.0.0; the prior plan to put new work into that version is obsolete.

The 1.13 upgrade clobbers a deliberate local partition override, invalidating the old assertion
that either migration order is safe. It also contains `ALTER TYPE ... ADD ATTRIBUTE` without an
idempotence guard: ledger-controlled reruns are safe, arbitrary replay of the raw script is not.

The existing partition test in `pgmq-hasql/test/QueueSpec.hs` skips if pg_partman is unavailable.
That is no longer enough to validate this initiative. Metrics use planner estimates summed
across queue and archive defaults; tests must ANALYZE both and must not promise instantaneous
exact counts in production.

The old grouped-head test used `qty = number of groups`, which can also pass for round-robin.
The revised child uses `qty` greater than the number of groups and tests blocked heads and
expiry explicitly.

The September 10 Mori inventory includes package-level users in `mori://shinzui/mori` and
`mori://shinzui/shikigami` as well as the previously recorded consumers. Keiro remains in the
rollout scope even though the current reverse-dependency report does not list it directly;
its registry still declares keiro-pgmq and its dependency on the Shibuya adapter. EP-12 must
inspect actual package sources and distinguish direct consumers from project-level references.
